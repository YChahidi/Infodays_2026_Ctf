# var_override — Writeup

**Category:** Cryptography · **Difficulty:** Extreme (single flag)

Classical Hidden Number Problem attack on ECDSA with biased nonces.
The signer source is handed to you explicitly — the bug is meant to
be found by reading, not guessing. The exploit is not a bypass: it
is a real cryptanalytic recovery of the private key, starting from
15 signatures and ending with an LLL-short vector that literally
contains `d`.

---

## 1. Reading the source

`signer.py` is a clean secp256k1 ECDSA implementation. The only
thing that looks even slightly weird is the nonce draw:

```python
# NONCE GENERATION
# The legacy VAR1 audit log packs each signed decision into a
# fixed 29-byte record: a 3-byte decision tag followed by the
# 232-bit nonce that was used to sign it. ...
k = secrets.randbits(232)
```

That comment is a lie of convenience. In ECDSA, the per-signature
nonce `k` is required to be **uniform over `[1, n)`** where `n` is
the curve order (for secp256k1, a 256-bit prime). Drawing only 232
bits means the **top 24 bits of every `k` are zero**. The signer is
publishing one linear equation per signature of the form

```
s · k ≡ z + r · d  (mod n)
```

with `k` much smaller than `n`. That is the Hidden Number Problem,
and HNP with a constant-size MSB leak is solvable by LLL using the
Boneh–Venkatesan lattice construction.

## 2. Setting up the linear relations

For each signature `(z_i, r_i, s_i)`:

```
s_i · k_i ≡ z_i + r_i · d (mod n)
⇒  k_i ≡ s_i^{-1} · z_i  +  s_i^{-1} · r_i · d  (mod n)
```

Define

```
A_i = s_i^{-1} · z_i  mod n      (known)
T_i = s_i^{-1} · r_i  mod n      (known)
```

Then for every signature

```
k_i ≡ A_i + T_i · d  (mod n)       ... (*)
```

We know `0 ≤ k_i < K` where `K = 2^{232}`, but we do **not** know
`k_i`, `d`, or the implicit reduction multiple `λ_i` in

```
A_i + T_i · d - λ_i · n = k_i
```

This is exactly the `m`-instance Hidden Number Problem with partial
MSB leak. The unknown `d` is the "hidden number."

## 3. Lattice construction (Boneh–Venkatesan)

Consider the `(m+2) × (m+2)` integer lattice generated by the rows:

```
        col 0   col 1   ... col m-1   col m    col m+1
row 0 : [ n²,    0,     ...   0,       0,        0   ]
row 1 : [ 0,     n²,    ...   0,       0,        0   ]
  ⋮
row m-1:[ 0,     0,     ...   n²,      0,        0   ]
row m : [ T₁·n,  T₂·n,  ...   Tₘ·n,    K,        0   ]
row m+1:[ A₁·n,  A₂·n,  ...   Aₘ·n,    0,        K·n ]
```

Take the integer linear combination `(λ₁, λ₂, …, λₘ, d, 1)` of these
rows. The resulting vector is

```
( n·k₁,   n·k₂,   …,   n·kₘ,   d·K,   K·n )
```

because `λᵢ·n² + d·Tᵢ·n + Aᵢ·n = n·(Aᵢ + Tᵢ·d + λᵢ·n) = n·kᵢ`
(from relation `(*)`), and the last two coordinates come straight
from `d·row_m + 1·row_{m+1}`.

Every coordinate of this vector is bounded in magnitude by about
`n·K`:

- `n·kᵢ < n·K`
- `d·K < n·K` (because `d < n`)
- `K·n = n·K`

So the target vector has Euclidean norm about `√(m+2) · n·K`.

The lattice determinant is

```
det L = (n²)^m · K · (K·n) = n^{2m+1} · K²
```

For `m = 15`, `n ≈ 2^{256}`, `K = 2^{232}`:

```
det L = 2^{31·256 + 2·232}  =  2^{8400}
```

Gaussian heuristic for the shortest vector in dimension 17:

```
λ₁(L) ≈ √(17 / (2πe)) · det^{1/17}
      ≈ 0.4 · 2^{8400/17}
      ≈ 2^{492}
```

Our target vector has norm `≈ √17 · 2^{488} ≈ 2^{490}`, comfortably
below the Gaussian bound. LLL finds it easily.

## 4. Extracting `d` from the LLL output

Run LLL on the basis and look for the row whose last entry is
`±K·n`. That is the image of our target vector (possibly flipped in
sign). The second-to-last entry of that same row is `±d·K`, so

```
d = (row[m] · sign) / K   (mod n)
```

Sanity-check by computing `k₀ = s₀^{-1}(z₀ + r₀·d) mod n` and
verifying `0 ≤ k₀ < K`. If yes, you have the private key.

## 5. The full solver

See `solver/solve.py`. Highlights:

```python
from fractions import Fraction as Fr

def lll_reduce(basis, delta=Fr(3, 4)):
    # Textbook LLL, rational arithmetic.
    ...

def build_lattice(sigs, n, K):
    m = len(sigs)
    T = [r * pow(s, -1, n) % n for z, r, s in sigs]
    A = [z * pow(s, -1, n) % n for z, r, s in sigs]
    dim = m + 2
    basis = [[0] * dim for _ in range(dim)]
    for i in range(m):
        basis[i][i] = n * n
        basis[m][i] = T[i] * n
        basis[m + 1][i] = A[i] * n
    basis[m][m] = K
    basis[m + 1][m + 1] = K * n
    return basis

def recover_d(sigs, n, K):
    reduced = lll_reduce(build_lattice(sigs, n, K))
    for row in reduced:
        if abs(row[-1]) != K * n:
            continue
        sign = 1 if row[-1] > 0 else -1
        scaled = row[-2] * sign
        if scaled % K:
            continue
        return (scaled // K) % n
    return None
```

LLL runs through `sympy.polys.matrices.DomainMatrix.lll`, which is
pure integer arithmetic on Python ints — the full attack finishes
in under 10 seconds on the 17-dim basis. `fpylll` or SageMath are
faster still but are not required.

## 6. Unwrapping the flag

Once `d` is recovered:

```python
import hashlib
from Crypto.Cipher import AES

key = hashlib.sha256(d.to_bytes(32, "big")).digest()
blob = open("public/flag.enc", "rb").read()
nonce, tag, ct = blob[:12], blob[12:28], blob[28:]
flag = AES.new(key, AES.MODE_GCM, nonce=nonce).decrypt_and_verify(ct, tag)
print(flag.decode())
# INFODAYS{SaamNoLimits_hnp_lattice_var_override_<hex>}
```

## 7. Why it's Extreme

- **Chain of ideas.** The bug is spotted by reading Python; the
  exploit is spotted by knowing ECDSA; the construction is known by
  reading Boneh–Venkatesan or Nguyen–Shparlinski; the implementation
  requires writing (or driving) LLL; the flag requires AES-GCM
  unwrapping from a derived key. Five distinct skills stacked.
- **No oracle, no server.** Everything is offline. Players cannot
  fish for additional signatures or chosen-message queries — they
  have exactly what was intercepted, and that has to be enough.
- **No bypass.** This is not "find a bug, skip the check." The flag
  is AES-GCM'd under a key derived from the actual private key. You
  cannot decrypt without recovering `d` first, and you cannot forge
  a ciphertext without `d`.
- **The cover story is convincing.** "232-bit nonces for legacy
  audit log compatibility" reads like a reasonable engineering
  constraint. Only a crypto person sees `randbits(232)` and
  immediately thinks *Wiener*, *Nguyen–Shparlinski*, *HNP*.
